## 1. 当前能力盘点

### 1.1 SearchResult 可用作总结证据的字段（代码事实）

| 字段 | paper (CNKI/万方/IEEE) | patent (万方专利) | news (天大新闻网) |
| --- | --- | --- | --- |
| title | ✅ | ✅ | ✅ |
| authors | ✅ | []（og 镜像后=发明人） | []（详情署名镜像后=记者） |
| **abstract** | **None（三源列表均不解析摘要，grep 零命中）** | ✅ 列表 `.abstract-area` | ✅ 列表 `p.desc` |
| artifact_metadata | — | inventors/applicant/publication_number/application_number/date | media/publish_time/authors/related_person |
| detail_url | ✅（CNKI/万方/IEEE） | resolver 点击捕获 | resolver 点击捕获 |
| 详情正文 | ❌ 无任何详情内容解析器 | 详情页有 摘要+主权项（未解析） | 详情全文（`_news_content_head` 1500 字瞬态） |

**关键审计发现（代码 grep 事实）**：`grep abstract cnki.py ieee.py wanfang.py`
零命中——**三个论文源当前均不产出摘要**。`SearchResult.abstract` 仅由
news（p.desc）、patent（abstract-area）与 demo 数据填充。

### 1.2 三类型详情获取能力与风险

| 类型 | 按需详情正文 | 风险 |
| --- | --- | --- |
| paper-CNKI | 详情页有摘要，但需打开 CNKI 详情页——验证码/风控风险最高 | ⚠️ 谨慎/低频 |
| paper-万方 | 详情页有摘要；与既有 WanfangMetadataResolver 同型 | 低 |
| paper-IEEE | 代理详情页有 Abstract；代理页偶发白屏 | 中 |
| patent | **`og:description` = 完整摘要**（10 json 取证）+ 详情 摘要/主权项 | 低 |
| news | 详情全文已在 `_news_content_head`（1500 字） | 最低 |

**结论：NO_PROVIDER。** 按任务 §十：不写接入、不硬编码 key、不使用私人
token、不新增付费服务；本阶段不执行真实 provider PoC（无条件可执行），
仅交付最小 provider interface 设计与 Phase 2.4-B 启动条件。

```python
# 最小 provider protocol（仅设计）
class SummaryProvider(Protocol):

        """输入 prompt，返回模型原始文本输出。实现方负责鉴权与端点。"""
```

  或学校 tju-llm 接口（如已开放）；任一即可，无则 v1 以 fake provider 完成

## 5. Schema（审计结论：四字段最小闭环足够）

```python
StructuredSummary:
    research_content: str   # paper:研究内容 / patent:解决的问题与技术目标 / news:报道事件
    core_technology: str    # 技术方案关键点（news:报道明确提及的关键技术）
    main_results: str       # 主要成果（patent:提出/实现的方案；news:报道的成果）
    application_value: str  # 应用价值（报道/专利描述的潜在应用）
```

- 全部 str；第一版不做嵌套 JSON/confidence/标签体系；
- **limitations 不单设字段**：证据不足直接写进对应字段值
  （"当前摘要未提供足够技术细节，无法可靠判断"）——与任务 §六示例一致，
  避免双通道表述；
- 内部附加 `source_basis`（abstract/detail/metadata/news_content，记录输入
  证据类型，UI 可不展示）。

四字段经审计可自然覆盖三类型（见 §上表语义映射），**不需要三套 SummaryService**。

## 6. Prompt 原则（硬要求）

1. 仅依据提供材料；不得使用模型背景知识补全具体论文/专利/新闻事实；
2. 材料不支持的字段必须输出"当前可获取信息不足，无法可靠判断"类表述；
3. artifact-specific context 注入（§5 语义映射），schema/解析器统一；
4. 明确要求输出纯 JSON（禁止多余说明；解析端容忍一次 markdown 围栏剥离）。

## 7. SummaryService 设计（仅设计）

`services/summary_service.py`：

```
collect_evidence(result, session?) -> EvidenceBundle
    paper:  title/authors/keywords + abstract（当前多为空）
            + bounded 详情摘要获取（万方/IEEE 优先，CNKI 谨慎）
    patent: title/inventors/applicant/abstract/IPC/publication_number
    news:   title/media/publish_time/summary + 详情正文（复用
            TjuNews 详情打开模式，content_head 放宽至 ~3000 字）
build_prompt(bundle, artifact_type) -> str
SummaryProvider.complete(prompt) -> raw
parse_structured(raw) -> StructuredSummary   # JSON / fenced JSON / 字段校验
    失败：一次本地提取重试；仍失败 -> SummaryError
cache: 进程级 dict，key = (artifact_type, detail_url or doi or pub-number)
    第一版 session memory，不落库
```

边界：Adapter 只负责获取真实数据，绝不调用 LLM；UI 不拼 prompt；
SummaryService 不做检索。

## 8. Detail enrichment 需求结论

- news：**无需新增**（content_head 已存在，放宽切片即可）；
- patent：**无需新增**（列表摘要已够 v1；og:description 为增强项，一行 meta 读取）；
- paper：**需要新增** bounded 详情摘要 resolver（万方/IEEE 优先、CNKI 谨慎/低频），
  或 v1 对 paper 采用元数据级诚实降级（"当前未获取到摘要…"）。
  建议：Phase 2.4-B v1 先交付 news+patent 全链路，paper 详情摘要作为同阶段
  第二步（万方/IEEE 先行，CNKI 视风控表现）。

## 9. Cache

key = (artifact_type, detail_url / doi / publication_number / 归一化标题 兜底)；
进程级 session memory（与既有 resolver 缓存同风格）；重复点击同一结果零消耗。

## 10. Thread

LLM 调用不得阻塞 PySide6 主线程。设计：独立 `SummaryWorker`（QObject + QThread，
与 DetailManager 同生命周期风格）：点击「关键信息整理」→ 按钮 loading 态 →
worker 线程完成 evidence 收集 + provider 调用 → 信号回主线程展示。
单飞保护：进行中再次点击忽略（防无上限 worker）；不改 SearchWorker 生命周期。

## 11. UI 最小方案

底部操作区（"查看推荐理由"旁）新增按钮：**「关键信息整理」**
（未选中结果禁用；检索中禁用）。展示复用 ExplanationDialog 同型模态：

```
AI 关键信息整理（artifact 类型标签）
研究内容：…
核心技术：…
主要成果：…
应用价值：…
──────────────
以上内容由 AI 根据当前可获取的摘要、正文及元数据整理，仅供参考，
不构成对原文的替代或权威结论。
```

与现有功能区分：推荐理由=评分解释、生成报告=书目报告、关键信息整理=内容
语义总结——三个入口独立，不合并。

## 12. Failure degrade（设计定稿）

| 场景 | 行为 |
| --- | --- |
| 无摘要/正文（paper 无 abstract 且详情获取失败） | 不调用 LLM；显示"当前可获取信息不足，无法生成可靠的关键信息整理。" |
| provider timeout | "AI 整理暂时不可用，请稍后重试。" |
| malformed output | 本地 JSON 提取/围栏剥离一次；仍失败按 provider 失败处理，不无限重试 |
| 详情获取失败 | 已有摘要则降级用摘要；无任何有效文本则不调用 LLM |
| 连续点击 | 单飞保护，进行中忽略 |

## 13. 未来测试设计（Phase 2.4-B）

- Evidence collection：paper 无摘要 / patent abstract / news content / 全缺；
- Prompt：三类型各一（快照断言关键词注入）；
- Parser：合法 JSON / markdown fenced / 缺字段 / 非法 JSON / 一次重试；
- SummaryService：provider success / timeout / error / cache 命中 / 证据不足不调用；
- UI：未选中禁用、loading、正常展示、error、连续点击单飞、关闭窗口 worker 安全；
- No hallucination：证据中不存在的字段 → 输出含"信息不足"表述（断言不要求补全）。

## 14. 风险

1. **provider 依赖用户授权**——无授权则 R13 演示只能展示"整理框架 + 诚实
   不足"占位，真实总结无法现场演示（最大不确定性，需尽早决策）；
2. paper 摘要需新增详情获取——CNKI 风控风险（低频+仅按需可缓解）；
3. 幻觉风险由 prompt 硬约束 + "信息不足"语义 + 免责声明共同压制，但无法归零；
4. 敏感文本外发：摘要/正文送第三方端点需用户知情（授权时一并确认）。

## 15. GO / PARTIAL / NO_GO

**PARTIAL → GO（Phase 2.4-B）**，附两个前置条件：
1. 用户提供/授权一个 LLM provider（OpenAI-compatible 或 tju-llm）；

2. paper 摘要获取作为 v1 内主要新增抓取工作（万方/IEEE 先行）。
