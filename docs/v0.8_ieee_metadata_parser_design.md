## 一、当前 IeeeAdapter 数据解析流程

### 1.1 流程

```
IEEE 搜索结果页
   ↓  DOM 提取（page.evaluate JS）
   ↓  _parse_results(page, count)   ieee.py:59
   ↓  逐条构造 SearchResult
   ↓  SearchResult
```

### 1.2 当前 selector / 正则 / 支持字段

| 字段 | 当前提取方式 | 代码位置 |
| --- | --- | --- |
| title | `h3 a.fw-bold` 的 innerText | ieee.py:63 |
| url | `h3 a.fw-bold` 的 href | ieee.py:64 |
| authors | `.author a` 列表 | ieee.py:65 |
| year | `_YEAR_RE = \b(20\d{2})\b` 在整条 innerText 上 search | ieee.py:18,67 |
| venue | `_VENUE_RE = \d{4}\s+(.+?)(?:\s*(?:Year:\|Conference:\|Journal:\|$))` 在整条 innerText 上 search | ieee.py:24,72 |
| document_type | `_DOC_TYPE_RE = Conference Paper\|Journals? & Magazines\|Early Access\|Standards\|Books\|Courses` 在整条 innerText 上 search | ieee.py:20,68 |

**核心问题**：所有元数据（year/venue/document_type）都用**正则对整条 `innerText` 匹配**，而非针对结构化 DOM 节点。

### 1.3 缺失字段根因（实测确认）

用当前正则对真实 innerText 测试：

| 条目类型 | 实际 innerText 片段 | year | venue | document_type |
| --- | --- | --- | --- | --- |
| 期刊（China Communications） | `China Communications\nYear: 2019 \| Volume: 16, Issue: 2 \| Magazine Article \| Publisher: IEEE\nCited by...` | `2019` ✅ | **None** ❌ | **None** ❌ |
| 会议（IRMMW-THz） | `2024 49th International Conference... (IRMMW-THz)\nYear: 2024 \| Conference Paper \| Publisher: IEEE` | `2024` ✅ | `49th International Conference...` ✅ | `Conference Paper` ✅ |

**根因 1：venue=null（期刊类）**
`_VENUE_RE` 要求 venue 文本**以 4 位年份开头**（会议风格 `2024 49th...`）。期刊类 venue（`China Communications`）在年份**之前**，且 `(.+?)` 中的 `.` **不跨换行**，而 venue 行后紧跟 `\nCited by...`，导致 `(?:\s*(?:Year:|Conference:|Journal:|$))` 的 `$` 无法命中（非串尾）→ 整条正则匹配失败 → venue=null。

**根因 2：document_type=null（期刊类）**
`_DOC_TYPE_RE` 只含 `Conference Paper|Journals? & Magazines|Early Access|Standards|Books|Courses`。而页面实际对期刊/杂志使用的标签是 **`Magazine Article`**（不在列表内）→ 不命中 → document_type=null。会议类 `Conference Paper` 命中正常。

**根因 3：year**
`_YEAR_RE` 在整条文本上 search，期刊/会议均能命中（`2019`/`2024`）。但**依赖整条文本**，若标题/作者名含 4 位数字会误匹配（潜在风险）。

## 二、IEEE 当前页面结构分析

### 2.1 真实 DOM 结构（探测确认）

每个结果项（`.List-results-items .result-item`）的元数据容器**结构化且稳定**：

```html
<div class="description text-base-md-lh">
  <a href="/xpl/RecentIssue.jsp?punumber=...">China Communications</a>
   <!-- ↑ venue：期刊名 或 会议名（首个 <a>） -->
  <div class="publisher-info-container">
    <span>Year: 2019</span>                      <!-- ↑ year -->
    <span> | <span>Magazine Article</span></span> <!-- ↑ document_type -->
    <span> | <xpl-publisher>...IEEE</xpl-publisher></span>
  </div>
  <div> Cited by: Papers (329)</div>
</div>
```

会议类结构完全一致，仅 venue 文本为 `2024 49th International Conference...`：

```html
<div class="description text-base-md-lh">
 <a href="/xpl/conhome/...">2024 49th International Conference ... (IRMMW-THz)</a>
 <div class="publisher-info-container">
   <span>Year: 2024</span>
   <span> | <span>Conference Paper</span></span>
   <span> | <xpl-publisher>...IEEE</xpl-publisher></span>
 </div>
</div>
```

### 2.2 各字段 DOM 节点与稳定性

| 字段 | DOM 节点 | 稳定性 | 是否需详情页 |
| --- | --- | --- | --- |
| title | `h3 a.fw-bold` | 稳定 | 否 |
| authors | `xpl-authors-name-list .author a` | 稳定 | 否 |
| **venue** | `.description a`（首个 `<a>`） | 稳定（期刊/会议均在此） | 否 |
| **year** | `.publisher-info-container span`（含 `Year:`） | 稳定 | 否 |
| **document_type** | `.publisher-info-container span`（匹配类型标签） | 稳定 | 否 |
| abstract / doi / keywords | 结果页**不可见** | — | **是**（需详情页） |

**结论**：venue/year/document_type 在**搜索结果页即可稳定获取**（结构化 DOM），**无需详情页**。abstract/doi/keywords 才需详情页。

## 三、修复方案比较

### 3.1 方案 A：继续优化搜索结果页解析（**推荐**）

**做法**：把正则改为**结构化 DOM 提取**（针对 `.description` / `.publisher-info-container` 节点），并扩充 `_DOC_TYPE_RE` 加入 `Magazine Article`。

```javascript
// 伪代码：在 evaluate 内直接读 DOM 节点
const desc = item.querySelector('.description');
const venue = desc ? desc.querySelector('a')?.innerText.trim() : null;
const pubInfo = item.querySelector('.publisher-info-container');
const yearMatch = pubInfo ? pubInfo.innerText.match(/Year:\s*(20\d{2})/) : null;
const docType = pubInfo ? pubInfo.innerText.match(
   /Conference Paper|Magazine Article|Journals? & Magazines|Early Access|Standards|Books|Courses/
) : null;
```

| 维度 | 评价 |
| --- | --- |
| 实现成本 | **低**。只改 `ieee.py` 的 `_parse_results` 内 JS 提取逻辑（venue/year/document_type 三处），不新增文件、不改 Adapter 接口 |
| 稳定性 | **高**。针对结构化 DOM 节点，不依赖文本顺序/换行，期刊/会议统一；比正则对整条 innerText 匹配稳健得多 |
| 对现有 Adapter 影响 | **低**。`search()` 流程、`SearchResult` 字段、返回结构不变；只提升字段填充率 |

**风险**：IEEE 前端若改版（Angular 组件类名变化）会失效；但 `.description`/`.publisher-info-container` 为语义化类名，相对稳定。建议加**解析失败兜底**（节点缺失时保持 None，不抛异常）。

### 3.2 方案 B：搜索页获取基础信息，详情页补充 metadata

**做法**：搜索结果页拿 title/authors/year/venue/document_type，再对每条 `detail_url` **进入详情页**抓 abstract/doi/keywords。

| 维度 | 评价 |
| --- | --- |
| 实现成本 | **中**。需新增详情页导航 + 解析逻辑（`session.open_detail` 已有）；每条结果一次额外页面加载 |
| 稳定性 | 中。详情页结构需探测；代理隧道/加载慢/验证码风险增加 |
| 对现有 Adapter 影响 | 中。`search()` 需改为"搜索 + 逐条进详情"，耗时显著增加（count 条 × 页面加载），违背"单次搜索/不进入详情页"的现有边界 |

**结论**：适合需要 abstract/doi/keywords 的**后续**需求；对当前 year/venue/document_type 缺失问题**过度**（这些字段结果页已有）。

### 3.3 方案 C：调用 IEEE API

**做法**：改用 IEEE Xplore REST API（需 API key）或元数据接口。

| 维度 | 评价 |
| --- | --- |
| 实现成本 | **高**。需申请 API key、处理鉴权/配额/限流；当前授权环境是**图书馆代理隧道**（`p.lib.tju.edu.cn` 代理落地页），非 IEEE 开放 API 环境 |
| 稳定性 | 中。API 返回结构化 JSON 最稳，但依赖外部服务与 key |
| 对现有 Adapter 影响 | **高**。完全重写数据获取路线，脱离现有代理隧道；与项目"复用已验证代理隧道"的哲学冲突 |

**结论**：**当前授权环境不适合**（是图书馆代理而非 API 环境），不推荐。

### 3.4 方案对比

| 维度 | A（优化结果页解析） | B（详情页补充） | C（IEEE API） |
| --- | --- | --- | --- |
| 实现成本 | **低** | 中 | 高 |
| 稳定性 | **高** | 中 | 中（依赖 key/配额） |
| 对现有 Adapter 影响 | **低** | 中 | 高 |
| 解决当前缺失 | **是**（venue/doc_type） | 是（但过度） | 是 |
| 适合当前代理环境 | **是** | 是 | **否** |
| 推荐度 | **推荐** | 暂缓（后续 abstract/doi 用） | 不推荐 |

## 五、结论

1. **根因**：当前用正则对整条 `innerText` 匹配元数据，`_VENUE_RE` 要求 venue 以年份开头（期刊类不满足且 `.` 不跨换行）→ venue=null；`_DOC_TYPE_RE` 缺 `Magazine Article` 标签 → document_type=null；year 正常。
2. **页面结构**：venue/year/document_type 在搜索结果页的**结构化 DOM**（`.description` / `.publisher-info-container`）中稳定可得，**无需详情页**。
3. **推荐方案 A**：结构化 DOM 提取，成本低、稳定性高、对现有 Adapter 影响小；只改 `ieee.py` 的 `_parse_results`。
4. **方案 B（详情页）**：留作后续获取 abstract/doi/keywords；**方案 C（IEEE API）**：当前代理环境不适合，不推荐。
