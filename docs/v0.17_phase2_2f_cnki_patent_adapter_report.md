## 1. 实现前两个最小探针

**A. 详情字段 selector（探针 17 json，连续 2 条取证）**
- 申请(专利)号 / 授权公告号(公开(公告)号) / 主分类号：详情页文本按行组织
  （`span.rowtit` 行标签取证），值 = 标签后至行尾；
- 摘要：body 文本 `摘要：` 起首行（首行自足）；
- 2 条详情字段形态一致，selector 非单页偶然。

**B. topic+inventor 组合语义（探针 14-16 json）**
- CNKI 无官方低成本多条件入口（"结果中检索"输入框与主搜索框同 id `#txt_search`，
  自动化不可稳定区分）；
- **生产方案：bounded local intersection**——以最选择性字段为基准
  （申请人 SQR > 发明人 AU > 主题 SU），用列表页元数据（标题/发明人列，
  均列表可得、无需开详情）本地验证其余条件；有硬上限、不伪装服务端 AND。

## 5. Resolver / CAPTCHA degrade

- 详情字段：application_number（申请(专利)号）、publication_number（授权公告号
  /公开(公告)号）、ipc（主分类号）、abstract（摘要首行）→ 写入
  `artifact_metadata` + `SearchResult.abstract`；
- **休眠验证码取证（探针 18 json）**：每详情页存在 id=captcha-element 的腾讯
  验证码元素（含“安全验证/拖动”文本），但内容完全可读——字段可得即成功；
  **仅当字段不可得 且 标记存在** 才判定真阻断并降级（日志
  “detail enrichment blocked”）；从不与验证码交互/绕过/重试轰炸。

## 6. CAPTCHA 处理总结

安全验证元素为休眠钩子（低频正常读取不触发）；resolver 坚持 bounded 低频，
出现真阻断（字段不可得）时停止该条并保留列表数据。

## Hotfix 记录（2026-09-08：topic + applicant 组合检索）

**GUI 人工发现的 bug**：研究方向=太赫兹、人员单位=天津大学、成果=仅专利、
数据库=仅 CNKI 时，返回手术器械/电池负极/机器人示教/FPGA 等明显与太赫兹无关的
天津大学专利——topic+applicant 未实现真实 AND。

**根因（代码级）**：
1. 基准选择 `affiliation > person > topic`（原代码）→ topic+applicant 走了
   `SQR(天津大学)` 基准；
2. intersection 分支**缺少 `original and affiliation` 情形** → 落空不过滤，
   直接返回 SQR 结果（全是天大专利、无 topic 证据）；
3. AND intersection 语义不严：本地验证未实现 positive-match-only。

**修复策略**（只改 `sources/cnki_patent.py`）：
1. **base query matrix 重设计**：person > topic > applicant——
   - topic only → SU；person only → AU；applicant only → SQR；
   - topic+applicant → **SU(topic) 基准** + 本地申请人严格验证
     （禁止 SQR 基准从海量单位专利前 N 条找主题）；
   - person+applicant → AU(person) + 本地申请人验证；
   - topic+person+applicant → AU(person) + 标题/申请人双验证；
2. **AND verifier（adapter 级）**：每个本地验证条件必须 positive MATCH——
   - topic：title 含 topic OR abstract 含 topic（详情 enrichment 提前到验证前，
     cap≤8）；无任何证据（UNKNOWN）→ 删除；
   - applicant：申请人字段明确包含单位；缺失（UNKNOWN）→ 删除；
   - person：发明人列包含姓名；
   - 刻意区别于 FilterService 的 unknown!=mismatch（二者职责不同，
     FilterService 与通用语义未改）；
3. **bounded 分页**（召回修正）：候选池尊重 result_count——第 1 页仅 20 条，
   SU=太赫兹 的天大专利位于第 21+ 位（探针 19 json 取证）→ 最多 ceil(count/20)
   页、硬上限 5 页（100 条），去重；
4. enrichment 提前：先补齐摘要供 topic 验证，再 intersection。

**测试**（tests/test_cnki_patent.py 25 → 31）：
- topic+applicant：A(标题含太赫兹+申请人天大)→保留；B(机器人+摘要无太赫兹)→删；
  C(机器人+无摘要=UNKNOWN)→删；D(太赫兹+其它单位)→删；
- 组合矩阵：topic+person、person+applicant（applicant 验证）、三条件；
- 分页：候选池 ≥ count 且按 count 截断、去重、5 页硬上限；
- FilterService unknown 语义不回归（既有测试锁定）。

**真机 probe**（runtime/v0.17_cnki_patent_probe/phase22f_hotfix_probe.json）：
太赫兹 + 天津大学（CNKI专利，result_count=40，跨 2 页候选）→

## Hotfix-2（2026-09-08：bounded local intersection 候选召回）

**最终验收结论：`HOTFIX_2 = PASS`。** 真实生产 probe、自动测试及不 deselect
全量回归均通过；未进入 Phase 2.4-C。

### 根因与新语义

Hotfix-1 的分页仍以 `ceil(result_count / 20)` 决定最大页数，并在 AND 验证前
通过 `_map_rows(rows, result_count)` 截断候选。因此 `result_count=5/20` 分别只会
检查第一页前 5/20 条，而已取证的“太赫兹 AND 天津大学”真实命中位于 SU 基查询
第 21+ 条，造成假阴性。

Hotfix-2 将两个预算彻底分离：

- `requested_output_count`：只用于停止累计 match 和最终 `matches[:count]`；
- `intersection_candidate_budget`：组合查询固定最多 5 个列表页、100 个去重候选，
  与 requested count 无关。

组合查询现在逐页执行：解析当前页 → 以 detail URL（缺失时使用列表复合键）稳定
去重 → 计入候选 hard cap → 先用 inventor/applicant 列表字段严格验证 → title 可证明
topic 时直接 MATCH，否则仅对仍可能匹配的候选尝试 bounded abstract enrichment →
只累计所有条件均 positive MATCH 的结果。达到 requested count、5 页、100 candidates、
无下一页、页面无新增候选或单次翻页失败中的任一条件即停止；翻页失败不重试。

Hotfix-1 的 base matrix 未改：`person > topic > applicant`；topic+applicant 使用
SU(topic)，person+applicant 使用 AU(person)，三条件使用 AU(person)。Adapter-level
AND 仍为 MATCH 保留、MISMATCH/UNKNOWN 删除，未修改 FilterService 的
`unknown != mismatch` 语义。

### 详情预算、安全与单条件

组合分页跨页共享同一详情预算：最多送交 resolver 8 个确需 abstract 证明 topic 的
候选；单项 timeout 仍为 5s，总预算仍为 30s。applicant 和 inventor 只读列表字段，
title 已证明 topic 时不打开详情；预算耗尽或详情不可得均为 UNKNOWN 并删除。未扩大
CAPTCHA 行为：仅关键内容不可读且出现验证状态时诚实降级，不交互、不绕过。

单条件 topic/person/applicant 保持原路径；例如 topic-only `count=5` 使用第一页并只
映射 5 条，不启用 5 页/100 candidate intersection 扫描。
