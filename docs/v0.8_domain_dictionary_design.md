## 一、当前 TERMS 数据结构

### 1.1 定义位置

`src/tju_info_retrieval/services/query_translator.py:19-28`

```python
TERMS: dict[str, dict[str, list[str]]] = {
    "太赫兹": {
        "en": ["terahertz", "THz"],
    },
    "通感一体化": {
        "en": [
            "integrated sensing and communication",
            "ISAC",
        ],
    },
}
```

- **结构**：`dict[str, dict[str, list[str]]]`——外层 key 为中文概念词，内层 key 为语言（当前仅 `"en"`），值为该语言的等价词列表。
- **当前规模**：仅 **2 条**（`太赫兹`、`通感一体化`），人工维护。

### 1.2 使用方式

| 使用点 | 位置 | 读取方式 |
| --- | --- | --- |
| `ConceptSegmenter` 词典 | `query_translator.py:80` | `ConceptSegmenter(set(TERMS.keys()))` — 取**所有 key** 作为切分词典 |
| 概念→英文映射 | `query_translator.py:82` | `TERMS.get(piece, {}).get("en")` — 整词精确匹配，未命中返回 `None` |

### 1.3 ConceptSegmenter 如何依赖

`ConceptSegmenter` **本身不引用 `TERMS`**，而是通过构造函数注入词典：

```python
class ConceptSegmenter:
    def __init__(self, dictionary: set[str] | None = None) -> None:
        self._dict = set(dictionary) if dictionary else set()
```

`QueryTranslator._concepts_for` 以 `set(TERMS.keys())` 作为词典传入。**依赖方向**：`QueryTranslator` → `ConceptSegmenter`（单向），`ConceptSegmenter` 不依赖 `TERMS`，从而避免循环导入。切分器只关心"哪些词是概念"（key 集合），不关心"概念映射到什么英文"（value）。

### 1.4 QueryTranslator 如何读取

```python
def _concepts_for(self, expanded: ExpandedQuery) -> list[list[str]]:
    concepts: list[list[str]] = []
    segmenter = ConceptSegmenter(set(TERMS.keys()))
    for piece in segmenter.segment(expanded.original):
        en = TERMS.get(piece, {}).get("en")   # 整词精确匹配
        if en:
            concepts.append(list(en))
        else:
            concepts.append([piece])          # 未命中保持原样
    return concepts
```

- **切分**：`segment()` 用 `TERMS` 的 key 集合做最长匹配，把中文串切成概念词列表。
- **翻译**：对每个切出的概念词，用 `TERMS.get(piece, {}).get("en")` 精确查英文等价词；命中替换，未命中保留中文。

## 二、设计领域词典扩展方案

### 2.1 方案 A：继续扩展 Python dict（当前方式）

**做法**：直接在 `query_translator.py` 的 `TERMS` 字面量里追加条目，如：

```python
TERMS = {
    "太赫兹":   {"en": ["terahertz", "THz"]},
    "通感一体化": {"en": ["integrated sensing and communication", "ISAC"]},
    "通信":     {"en": ["communication"]},
    "无线通信":  {"en": ["wireless communication", "wireless"]},
    "毫米波":    {"en": ["millimeter wave", "mmWave"]},
}
```

| 维度 | 评价 |
| --- | --- |
| **可维护性** | 差（几十/几百词后）。词典与翻译逻辑同文件，`query_translator.py` 被词典数据膨胀；多人并行编辑易冲突；无法按领域（太赫兹/通信/毫米波）分组维护 |
| **测试影响** | 低。现有 `test_query_translator.py` 的 `test_terms_dict_has_expected_entries` 只断言 `太赫兹`/`通感一体化` 存在，追加条目不影响；`test_concept_segmenter.py` 用 `set(TERMS.keys())` 动态取词典，自动跟随 |
| **后续扩展几十/几百词** | 差。单文件字面量难以组织、难以审查、难以按领域分类；无校验（拼写错误、重复 key 静默覆盖） |

**结论**：适合**个位数**词条；不适合规模化。

### 2.2 方案 B：独立 `terminology.py`

**做法**：新增 `src/tju_info_retrieval/services/terminology.py`，把词典数据与翻译逻辑分离：

```python
# terminology.py —— 领域词典数据（纯数据，无逻辑）
TERMS: dict[str, dict[str, list[str]]] = {
    "太赫兹":   {"en": ["terahertz", "THz"]},
    "通感一体化": {"en": ["integrated sensing and communication", "ISAC"]},
    "通信":     {"en": ["communication"]},
    "无线通信":  {"en": ["wireless communication", "wireless"]},
    "毫米波":    {"en": ["millimeter wave", "mmWave"]},
}
```

`query_translator.py` 改为 `from tju_info_retrieval.services.terminology import TERMS`。

| 维度 | 评价 |
| --- | --- |
| **可维护性** | 中。词典独立成文件，`query_translator.py` 专注翻译逻辑；可**按领域分模块**（如 `terminology/terahertz.py`、`terminology/communication.py`）进一步分组；仍为 Python 字面量，可加注释、可编程生成 |
| **测试影响** | 低。测试 `from ...query_translator import TERMS` 需改为 `from ...terminology import TERMS`（`test_query_translator.py:20`、`test_concept_segmenter.py:19` 两处 import 调整）；断言逻辑不变 |
| **后续扩展几十/几百词** | 中。可维护性优于方案 A；可引入**模块级校验**（如 `__init__` 检查 key 非空、value 非空、无重复）；但仍是**硬编码 Python**，改词需改码、需重新发布 |

**结论**：适合**几十词**规模；比方案 A 清晰，但仍是代码内数据。

### 2.3 方案 C：JSON/YAML 外部词典

**做法**：新增 `data/terminology.json`（或 `.yaml`），与代码分离：

```json
{
  "太赫兹":   {"en": ["terahertz", "THz"]},
  "通感一体化": {"en": ["integrated sensing and communication", "ISAC"]},
 "通信":     {"en": ["communication"]},
 "无线通信":  {"en": ["wireless communication", "wireless"]},
 "毫米波":    {"en": ["millimeter wave", "mmWave"]}
}
```

`terminology.py` 负责加载：`json.loads(Path("data/terminology.json").read_text(...))`。

| 维度 | 评价 |
| --- | --- |
| **可维护性** | 高。数据与代码完全分离，**非开发者**（领域专家/图书管理员）可直接编辑 JSON 扩充词条，无需改代码、无需重新发布；可按领域分多个 JSON 文件 |
| **测试影响** | 中。需处理**文件路径**（`data/` 相对路径在测试/打包/不同 CWD 下可能不一致）；需处理 **JSON 解析失败** 与 **schema 校验**；现有 `test_terms_dict_has_expected_entries` 需适配加载函数 |
| **后续扩展几十/几百词** | 高。最适合规模化；但引入**文件 I/O 依赖**与**加载时机**问题（模块导入时加载 vs 惰性加载），且违背项目"纯逻辑、零外部文件依赖"的现有测试哲学（现有 `QueryExpansion`/`QueryTranslator`/`ConceptSegmenter` 均无文件 I/O） |

**结论**：最适合**几百词**规模化，但引入文件 I/O 与路径/加载复杂度，与项目纯逻辑测试哲学冲突。

### 2.4 方案对比

| 维度 | A（扩展 dict） | B（独立 terminology.py） | C（JSON/YAML 外部） |
| --- | --- | --- | --- |
| 可维护性 | 差 | 中 | **高** |
| 测试影响 | 低 | 低（仅 2 处 import 调整） | 中（路径/加载/schema） |
| 几十词扩展 | 差 | **中** | 高 |
| 几百词扩展 | 差 | 中 | **高** |
| 非开发者可编辑 | 否 | 否 | **是** |
| 文件 I/O / 路径依赖 | 无 | 无 | **有** |
| 与纯逻辑测试哲学一致 | **是** | **是** | 否 |
| 推荐度（当前 2 词规模） | 不推荐 | **推荐** | 暂缓 |

**推荐**：当前仅 2 词，**方案 B（独立 `terminology.py`）** 是平衡点——把词典从翻译逻辑中解耦、可维护、测试影响小、与纯逻辑哲学一致。若未来扩展到**几百词**且需非开发者维护，再迁移到方案 C（JSON），届时 `terminology.py` 只改加载实现，翻译/切分逻辑不动。

## 三、设计词典优先级规则

### 3.1 问题背景

词典扩展后会出现**包含关系**的词条，如：

- `无线通信` 包含 `通信`；
- `毫米波` 包含 `波`。

若 `无线通信` 与 `通信`、`毫米波` 与 `波` 同时入典，切分时需避免**最长匹配冲突**（把 `无线通信` 误切成 `无线`+`通信`，或把 `毫米波` 误切成 `毫米`+`波`）。

### 3.2 关键发现：最长匹配天然解决冲突

用当前 `ConceptSegmenter` 最长匹配算法实测（词典含 `太赫兹`/`通感一体化`/`通信`/`无线通信`/`毫米波`/`波`）：

```
'无线通信'      -> ['无线通信']      # 最长匹配：无线通信（4字）优先于 通信（2字）
'毫米波'        -> ['毫米波']        # 最长匹配：毫米波（3字）优先于 波（1字）
'通信'         -> ['通信']
'波'           -> ['波']
'太赫兹通信'     -> ['太赫兹', '通信']
'无线通信系统'   -> ['无线通信', '系统']
```

**结论**：`_longest_match` 从**最长到最短**尝试（`range(len(text), start, -1)`），因此**更长的词条天然优先**。只要词典同时含 `无线通信` 与 `通信`，`无线通信` 一定先命中，`通信` 只在 `无线通信` 不匹配（如单独 `通信` 或 `太赫兹通信`）时才命中。**无需额外优先级规则**，最长匹配本身就是优先级规则。

### 3.3 需要显式规则的场景（边界）

最长匹配虽解决**包含关系**冲突，但需注意以下边界，建议用**约定**而非代码规则约束：

| 场景 | 建议约定 |
| --- | --- |
| **同前缀不同词**（如 `通信` 与 `通信系统`） | 最长匹配自动选长词，无需规则 |
| **词条间无包含关系但共享字**（如 `太赫兹` 与 `赫兹`） | 最长匹配自动选长词；建议**只收录完整领域词**，不收录子串（避免 `赫兹` 这类碎片入典） |
| **同中文词多英文**（`太赫兹` → `terahertz`/`THz`） | 已是 list，`QueryBuilder` 用 `OR` 连接，无需规则 |
| **英文短语含空格**（`integrated sensing and communication`） | 已是 list 元素，`QueryBuilder._quote` 加引号，无需规则 |
| **未知词**（`量子计算`） | 整段保留，安全回退，无需规则 |

### 3.4 建议的词典维护约定（优先级规则落地）

1. **收录完整领域词，不收录子串**：只收录 `无线通信`、`毫米波` 这类完整概念，不收录 `通信`、`波` 的子串碎片——除非该子串本身是**独立概念**（如 `通信` 单独成词，应独立收录）。
2. **长词优先**：最长匹配自动保证 `无线通信` > `通信`、`毫米波` > `波`，无需人工排序。
3. **无重复 key**：同一中文词只出现一次（Python dict 天然去重，但建议在 `terminology.py` 加校验防静默覆盖）。
4. **value 非空**：每个概念的 `en` 列表至少 1 个等价词（避免空翻译）。

## 四、结论

1. **当前 TERMS**：`query_translator.py:19` 的 `dict[str, dict[str, list[str]]]`，仅 2 词；`ConceptSegmenter` 经 `set(TERMS.keys())` 取 key 做最长匹配，`QueryTranslator` 用 `TERMS.get(piece, {}).get("en")` 精确翻译。
2. **推荐方案 B**：独立 `terminology.py` 把词典数据与翻译逻辑解耦，可维护、测试影响小（仅 2 处 import 调整）、与纯逻辑哲学一致；几百词规模再迁方案 C（JSON）。
3. **优先级规则**：**最长匹配天然解决包含关系冲突**（`无线通信` > `通信`、`毫米波` > `波`），无需额外代码规则；只需约定"收录完整领域词、不收录子串碎片"。
4. **配套**：`通信`→`communication` 等词条加入词典后，`太赫兹通信` 才能完整翻译（当前 `通信` 保留中文）。
