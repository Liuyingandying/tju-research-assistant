# v0.9.3 论文整理能力前置只读审计

日期：2026-09-03 性质：**只读分析，未修改任何源码，未新增功能**

## 0. 背景与目标

当前系统已完成检索管线（v0.8.x 跨语言检索）+ 现代 UI（v0.9.0）+ 语言筛选（v0.9.1）+ IEEE 双入口（v0.9.2）。
用户检索到文献后，**结果仅在内存中存活**——关闭程序即全部丢失，无收藏/标签/备注/持久化能力。

本轮目标：审计现有架构，设计**最小改动方案**实现基础论文整理能力（收藏、本地保存、标签、备注、后续导出）。

## 1. SearchResult 数据模型审计

### 1.1 当前字段（`models/result.py`）

| 字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `rank` | int | ResultMerger 生成 | 排序序号 |
| `title` | str | 结果页 DOM | 论文标题 |
| `authors` | list[str] | 结果页 DOM | 作者列表 |
| `source` | str \| None | 结果页 DOM | 来源（期刊/会议名） |
| `year` | str \| None | 结果页 DOM | 年份 |
| `detail_url` | str \| None | 结果页 DOM | 全文链接（IEEE 为代理 URL） |
| `document_type` | str \| None | 结果页 DOM | 文献类型 |
| `database` | str | 适配器硬编码 | CNKI/万方/IEEE Xplore |
| `abstract` | str \| None | v0.4 预留，IEEE 未填 | 摘要 |
| `doi` | str \| None | v0.4 预留，IEEE 未填 | DOI |
| `keywords` | list[str] | v0.4 预留，IEEE 未填 | 关键词 |
| `venue` | str \| None | 实验性 | 会议/期刊名称 |
| `authors_raw` | str \| None | 原始作者字符串 | |

### 1.2 评估：是否足够作为收藏记录基础？

**结论：不够，但扩展成本低。**

缺失字段（从用户整理需求角度）：

| 缺失字段 | 用途 | 类型 | 是否新增到 SearchResult |
| --- | --- | --- | --- |
| `is_favorited` / `favorite` | 标记收藏状态 | bool | ❌ 不应加——收藏是用户行为，与检索结果无关 |
| `tags` | 标签列表 | list[str] | ❌ 不应加——标签属于用户元数据 |
| `notes` | 备注/批注 | str | ❌ 不应加——同上 |
| `saved_at` | 收藏时间 | datetime | ❌ 不应加——属于持久化层 |
| `id` / `uuid` | 唯一标识 | str | ✅ 建议加——用于精确匹配收藏记录 |

**核心判断**：收藏、标签、备注是**用户行为产生的元数据**，与检索结果本身的元数据（标题、作者、年份等）属于不同语义层。直接往 `SearchResult` 加字段会：

1. 污染检索结果模型——检索结果不应包含用户偏好状态；
2. 与 `ResultMerger` 去重逻辑耦合（`to_dict` 新增字段影响导出/报告）；
3. 与 `demo_data.py` 内置数据不兼容（demo 数据无收藏字段）；
4. 与 `export.py` 的 `EXPORT_FIELDS` 硬编码列表不兼容。

### 1.3 建议：新建 `LibraryRecord` 模型

```python
# models/library.py
@dataclass
class LibraryRecord:
    id: str                     # 唯一标识（uuid4 或 title+author+year 哈希）
    # --- 从 SearchResult 复制的元数据 ---
    title: str
    authors: list[str]
    source: str | None
    year: str | None
    detail_url: str | None
    document_type: str | None
    database: str
    venue: str | None
    doi: str | None
    # --- 用户行为产生的元数据 ---
    tags: list[str]             # 标签列表
    notes: str                  # 备注文本
    is_favorited: bool = False  # 收藏标记
    saved_at: str = ""          # 收藏时间（ISO 格式）
    last_viewed_at: str = ""    # 最后查看时间
```

**优势**：
- 检索管线（SearchResult → merger → ranking → export → report）完全不受影响；
- 收藏记录独立存储，可自由扩展字段（如阅读进度、评分等）；
- 与 `demo_data.py`、`export.py`、`report_generator.py` 零耦合；
- 从 SearchResult 到 LibraryRecord 的转换是一次性函数（`SearchResult.to_library_record()`）。

## 2. 当前结果生命周期审计

### 2.1 数据流追踪

```
搜索完成
  ↓
SearchService.search() → list[SearchResult]
  ↓
Worker.search() → self._worker.search_done.emit([r.to_dict() for r in results])
  ↓
MainWindow._on_search_done(results: list[dict])
  ↓
self._results = results          ← 内存 list[dict]，生命周期 = MainWindow 实例
  ↓
_populate_table(results)         ← QTableWidget 仅显示 title/author/source/year/type/database
  ↓
用户点击"打开全文页面"
  ↓
self._results[sel].get("detail_url")  ← 从内存读取
```

### 2.2 关键发现

| 问题 | 影响 |
| --- | --- |
| 结果以 `list[dict]` 存储在 `MainWindow._results` | 程序关闭即全部丢失 |
| QTableWidget 仅存储显示文本（title/author 等），不存储完整元数据 | 无法从表格行反向恢复完整记录 |
| `_last_query_info` 保存检索条件 | 可复用为收藏记录的检索上下文 |
| `SearchResult.to_dict()` 已包含所有元数据 | 导出/报告已证明序列化可行 |
| `demo_data.py` 以 JSON dict 列表形式存储演示数据 | 证明 JSON 存储方案在项目中已有先例 |

### 2.3 结论

当前系统**无持久化能力**。要实现收藏/标签/备注，需要：

1. 新增持久化存储层（JSON 或 SQLite）；
2. 新增 `LibraryRecord` 模型；
3. 在 GUI 层提供收藏/编辑/导出接口；
4. **不修改**检索管线（SearchResult、merger、ranking、export、report）。

## 3. 报告生成与导出审计

### 3.1 `report_generator.py`

- `generate_markdown(results, query_info)`：纯函数，接受 `list[dict]`（`SearchResult.to_dict()` 输出）；
- 输出 Markdown 检索报告，包含检索条件、数据源统计、文献列表；
- `write_markdown(content, path)`：UTF-8 写出文件；
- **不涉及收藏/标签/备注**——报告是检索结果的快照，非用户整理产物。

### 3.2 `export.py`

- `export_json` / `export_csv` / `export_markdown`：固定字段 `EXPORT_FIELDS`（13 个）；
- 纯函数，接受 `Iterable[dict]`；
- **不涉及收藏/标签/备注**。

### 3.3 是否可以复用？

**可以，但需扩展**。收藏记录的导出应复用现有导出框架：

- `export_json` 可直接用于导出收藏库（JSON 格式天然适合嵌套 tags/notes）；
- `export_csv` 需扩展 `EXPORT_FIELDS`（或新增 `LIBRARY_EXPORT_FIELDS`）；
- `export_markdown` 可复用 `_rows` 逻辑，新增"标签"、"备注"列。

**建议**：新增 `export_library_records(records, path, fmt)` 入口函数，内部复用现有导出逻辑，新增字段追加到导出列。

## 4. 数据存储方案比较

### 4.1 方案 A：直接 JSON 文件

```python
# 存储路径：runtime/library.json（或项目根目录 library.json）
# 格式：
{
    "version": 1,
    "records": [
        {
            "id": "uuid4",
            "title": "...",
            "tags": ["太赫兹", "综述"],
            "notes": "这篇是综述，适合入门",
            "is_favorited": true,
            "saved_at": "2026-09-03T10:00:00",
            ...
        }
    ]
}
```

| 维度 | 评估 |
| --- | --- |
| 实现复杂度 | **极低**——Python 内置 `json` 模块，读写 30 行代码 |
| 标签/笔记扩展 | 天然支持——JSON 对象可嵌套任意字段 |
| 测试影响 | 新增测试即可，不触碰现有 278 测试 |
| 数据迁移 | 简单——JSON Schema 演进只需版本字段 + 迁移函数 |
| 并发安全 | 不需要——单用户桌面应用，单线程读写 |
| 查询能力 | 弱——需全量加载到内存后 Python 过滤 |
| 数据量上限 | 合理——单用户收藏通常在 100-5000 条，JSON 可承受 |
| 项目一致性 | 高——`demo_data.py` 已用 JSON 存储，`runtime/` 目录已纳入 `.gitignore` |

### 4.2 方案 B：SQLite 本地数据库

| 维度 | 评估 |
| --- | --- |
| 实现复杂度 | **中等**——需建表、索引、迁移脚本；Python 内置 `sqlite3` |
| 标签/笔记扩展 | 需多表设计（records + tags 多对多），复杂度上升 |
| 测试影响 | 新增测试，但需处理临时数据库文件 |
| 数据迁移 | 标准 SQL 迁移，但小项目过度设计 |
| 并发安全 | 内置 WAL 模式支持，但桌面单用户不需要 |
| 查询能力 | 强——支持 SQL 过滤、排序、全文搜索 |
| 数据量上限 | 高——万级记录无压力 |
| 项目一致性 | 低——项目目前无数据库依赖，引入 SQLite 是首个 |

### 4.3 方案 C：扩展现有数据文件

即往 `demo_results.json` 或新建 `runtime/results.json` 追加收藏字段。

| 维度 | 评估 |
| --- | --- |
| 实现复杂度 | 低 |
| 标签/笔记扩展 | 差——与检索结果混合，语义混乱 |
| 测试影响 | 可能破坏 `demo_data.py` 或导出逻辑 |
| 数据迁移 | 困难——检索结果与收藏记录混在一起 |
| **结论** | **不推荐**——语义层混淆，长期维护成本高于新建模型 |

### 4.4 推荐：方案 A（JSON 文件）

- 实现复杂度最低，与项目现有 JSON 存储实践一致；
- 单用户桌面应用，查询需求（按标签过滤、按关键词搜索）在内存中即可完成；
- 后续若需迁移到 SQLite，`LibraryRecord` 模型可保持不变，仅替换存储后端；
- JSON 文件放在 `runtime/library.json`（已纳入 `.gitignore`），不污染代码仓库。

## 7. 结论与建议

v0.9.3 最小实现方案：

1. **新建 `models/library.py`**：`LibraryRecord` 数据类 + `SearchResult` 转换函数；
2. **新建 `services/library_store.py`**：JSON 文件读写（`runtime/library.json`）；
3. **修改 `main_window.py`**：新增"收藏当前选中"按钮 + handler；
4. **扩展 `services/export.py`**：新增 `export_library_records()` 入口；
5. **新增测试**：模型 + 存储 + GUI 集成，总计 ~130 行测试代码；
6. **不修改**检索管线任何文件。

预计改动量：~200 行代码 + ~130 行测试，2 个新文件 + 2 个修改文件，风险低，测试影响为零。
