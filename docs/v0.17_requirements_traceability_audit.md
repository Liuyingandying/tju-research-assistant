## 4. 五个最高风险缺口

1. **R14 人名独立路径不可达**：UI、Request、Service、Expansion 四层都要求研究方向；这不是 adapter 小问题，而是完整用户路径缺失。
2. **R10 专利完全缺失**：无入口、请求语义、adapter、parser、模型字段、测试或真机产物。
3. **R7 + R12 中文新闻来源与新闻结果同时缺失**：即使课程老师只抽查“新闻”，系统也无法展示跨类型能力。
4. **R13 关键信息总结缺失**：当前只整理书目元数据；没有核心技术、主要成果、应用价值的结构化生成与证据边界。
5. **R2 扩展方向是跨源不一致的半实现**：四个 UI 标签与纯逻辑存在，但万方和 IEEE 没有消费方向 filters。

R3 人名三源能力紧随其后：它与 R14 应合并为第一项工程任务。

## 5. 逐链关键结论

### 5.1 扩展方向并非“只有 UI”但仍不合格

`QueryExpansionService` 已为理论/应用/综述生成不同词组：

- 理论：理论、机理、原理、模型、算法；
- 应用：应用、系统、装置、实现、工程；
- 综述：综述、进展、研究现状、展望、回顾。

这确实改变 CNKI 的中文 query。但 `QueryTranslator._concepts_for()` 只从 `expanded.original` 构造 IEEE 概念组，方向 filters 丢失；万方 adapter 为避免该站误把 Boolean 串当字面文本而明确改用 original keyword。因此 R2 只能是 PARTIAL。

### 5.2 人员姓名组合语义

| 路径 | 当前行为 | 判定 |
| --- | --- | --- |
| 方向非空、姓名空 | 三源正常检索 | 可用 |
| 方向非空、姓名非空 | CNKI native 作者条件；万方/IEEE先按方向检索再按结果 authors 过滤 | 部分可用 |
| 方向空、姓名非空 | UI 即拦截；Request/Service/Expansion 也会拒绝 | 不可用 |
| 姓名 + 单位，方向非空 | CNKI native 组合；万方 native 单位 + 本地作者过滤；IEEE详情单位增强 + 本地双过滤 | 来源语义不一致 |
| 姓名 + 单位，方向空 | 同样被方向必填阻断 | 不可用 |

现有测试能证明字段映射、CNKI表单构造和本地 FilterService，但不能证明万方/IEEE的人名召回率，也没有三源真人名 E2E。

### 5.3 单位 soft/strict 的真实边界

- CNKI：高级检索原生作者单位；成功后写 `source_verified`，soft/strict 均可有证据地保留。
- 万方：官方高级检索作者单位可用；当前 strict 在缺单位 metadata 时实施“来源保护保留”，因此不会归零，但也不是字面意义的严格匹配。
- IEEE：详情页按需提取 affiliation 后本地匹配；GUI 明确禁止含 IEEE 的 strict。

所以 R4 能用但不统一，不能判 PASS。

## 6. “等”的最小充分覆盖策略

### 6.1 9 月 28 日前必须形成的形态

**论文 + 专利 + 中文新闻 + 选中条目关键信息总结**。

理由：

- 论文已经成熟，继续增加排序不会增加任务书覆盖面；
- 专利提供“科研成果”类型，字段结构与论文明显不同，最能证明统一系统不是论文搜索器；
- 中文新闻提供“网站来源 + 新闻结果”双重覆盖，一次补 R7/R12；
- 对任一选中条目生成核心技术/主要成果/应用价值，直接回应评分中的“整理关键信息”。

### 6.2 著作与获奖

- **著作：B，后续扩展。** IEEE 搜索结果偶尔含 Books 不能算实现。若 P0 提前完成，可在统一模型上做一个小型 PoC；不应先于专利/新闻/总结。
- **获奖：B，后续扩展。** 数据标准化与稳定来源成本较高；9 月 28 日前只保证模型可扩展，并在路线中给出 PoC/停止条件。
- **统一 Web/搜索源：C，仅作为低成本补充，不作为 PASS 证据。** 通用网页搜索可用于探索，但没有 typed parser、字段映射、测试和真实 URL 证据时，不能将著作/获奖从 MISSING 改判为 PASS。

## 7. 多类型统一结果模型审计

### 7.1 当前问题

`SearchResult` 的核心字段是 `title/authors/source/year/detail_url/document_type/database/doi/venue/citation_count`，明显以论文为中心。它无法自然表达：

- 专利：applicant、inventor、publication_number、application_number、patent_status；
- 新闻：media、publish_time、article_url、related_person、related_institution；
- 获奖：award_name、award_level、award_year、organization；
- 图书：publisher、ISBN。

继续直接追加所有字段会产生大量互斥 optional 字段，使 parser、导出、UI 和缓存难以辨认类型契约。

### 7.2 方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 扩 SearchResult | 改动最小 | 论文中心化加剧；大量空字段；类型约束弱 | 不推荐 |
| B 新建单一 ResearchArtifact 并放所有字段 | 有统一入口 | 若仍平铺字段，本质与 A 相同；迁移面大 | 不单独采用 |
| C base model + typed metadata | 共同字段稳定；专利/新闻/论文各自有明确字段；可渐进兼容 | 需要兼容转换和类型渲染 | **推荐** |

推荐最小契约：

```python
ResearchArtifact(
    id,
    artifact_type,       # paper / patent / news / book / award
    title,
    source_name,
    source_url,
    published_at,
    contributors,
    summary,
    metadata,            # PaperMetadata | PatentMetadata | NewsMetadata | ...
)
```

Phase 1 不应一次迁移全部论文代码。先提供 `SearchResult -> ResearchArtifact` 兼容转换；新增专利/新闻 adapter 直接产出 artifact，再让 merge/display/export 逐步消费共同协议。

## 8. 关键信息总结最低可行架构

```text
用户选中 Result / ResearchArtifact
        ↓
DetailTextProvider（优先摘要，其次允许访问的详情文本）
        ↓
ContentExtractor（清洗、长度限制、来源片段）
        ↓
SummaryService（provider 可注入）
        ↓
StructuredSummary
  research_content / core_technology /
  main_results / application_value
        ↓
详情窗口 + 缓存 + 报告/导出（标记“AI总结”）
```

最低安全/失败语义：

1. 没摘要：尝试详情页可见文本；仍无内容则显示“来源文本不足”，不让模型猜测。
2. 详情页打不开：保留已有 metadata，summary 状态为 `source_unavailable`，不阻塞搜索。
3. LLM 失败：返回可重试错误；不覆盖历史成功缓存，不把错误文本写进成果字段。
4. 只总结用户主动选中的一条；不得默认同步总结 20/30 篇。
5. 输入上限、超时和一次调用预算固定；UI 明示“正在生成”。
6. 缓存键使用 `artifact identity + source_text_hash + prompt_schema_version + model_id`。
7. 输出必须显示“AI 总结”，保留来源链接和可用的原文摘要，禁止伪装为原文摘录。
8. 每个字段允许 `insufficient_evidence`；模型必须基于提供文本，不补写未出现的数字、结论或机构。
9. 当前仓库没有 TJU LLM/provider 实现；Phase 1 必须先用可注入 fake 完成离线契约，再决定是否接现有外部能力。
