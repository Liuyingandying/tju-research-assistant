## 一、审计当前 Adapter 接收的 query 格式

### 1.1 三个 Adapter 的 search 入口

三个 Adapter 的 `search(keyword, count)` 都把 `keyword` **原样填入各自搜索框**，无任何布尔预处理：

| Adapter | 填入方式 | 代码位置 | 接收的 query 格式 |
| --- | --- | --- | --- |
| `CNKIAdapter` | `search_input.fill(keyword)` + `search_button.click()` | `cnki.py:38-39` | 字符串（当前为中文布尔串） |
| `WanfangAdapter` | `page.fill("#search-input", keyword)` | `wanfang.py:40-41` | 字符串（当前为中文布尔串） |
| `IeeeAdapter` | `search_input.fill(keyword)`（`input[type=search]`） | `ieee.py:40-41` | 字符串（当前为英文空格串） |

### 1.2 是否支持 AND/OR/引号/括号

| Adapter | AND/OR | 引号 `"..."` | 括号 `()` | 说明 |
| --- | --- | --- | --- | --- |
| CNKI | 依赖 CNKI 引擎语法 | 依赖 CNKI 引擎语法 | 依赖 CNKI 引擎语法 | Adapter 只透传字符串，语法由 CNKI 检索框解析；当前收到 `(A OR B) AND (C OR D)` 中文布尔串（来自 `QueryExpansionService._build_query_string`） |
| 万方 | 依赖万方引擎语法 | 依赖万方引擎语法 | 依赖万方引擎语法 | Adapter 只透传字符串；当前收到同一中文布尔串 |
| IEEE | 依赖 IEEE 引擎语法 | 依赖 IEEE 引擎语法 | 依赖 IEEE 引擎语法 | Adapter 只透传字符串；当前收到**英文空格串**（Phase 1，无布尔） |

**关键结论**：Adapter 层对 query 语法**完全透明**——它不解析、不校验、不生成布尔结构，只是把字符串填进搜索框。因此：
1. **布尔/引号/括号的支持与否，取决于各数据库引擎**，而不是 Adapter；
2. 当前 CNKI/万方收到中文布尔串（`expanded.query_string`），IEEE 收到英文空格串——**三者格式不一致**，这正是 QueryBuilder 要统一/优化的点。

## 二、分析 QueryBuilder 插入位置

### 2.1 当前调用链（Phase 1）

```
SearchService.search()
  expanded = QueryExpansionService.expand(direction, expansion_direction)   # 中文布尔串
  queries = QueryTranslator.translate(expanded, sources)                    # {源: 串}
  for source in sources:
       adapter.search(queries[source_name], count)                          # 原样填入
```

### 2.2 方案 A：QueryTranslator 直接输出最终 query

```
QueryTranslator.translate(expanded, sources) -> {源: 最终query串}
```

- **架构影响**：翻译与"数据库语法适配"耦合在同一个类。`QueryTranslator` 既要管"中文→英文概念"，又要管"英文概念→IEEE 布尔语法"。职责过重。
- **后续扩展 WoS/Scopus**：每加一个库，都要在 `QueryTranslator` 里加语法分支，翻译逻辑与语法逻辑混杂，易膨胀。
- **对现有测试影响**：`test_query_translator.py` 断言的是空格串输出（Phase 1 行为），若改为输出布尔串，这些断言需改；且 `test_search_service.py:56/61/71` 单源断言（adapter 收到 `Q`/`量子计算`）依赖 CNKI 透传，若 CNKI 也走 QueryBuilder 需确认透传不变。

### 2.3 方案 B：QueryTranslator 输出概念，QueryBuilder 生成数据库 query（**推荐**）

```
QueryTranslator.translate(expanded, sources) -> {源: 概念列表/结构化}
QueryBuilder.build(source, translated_terms)  -> 该库最终query串
```

- **架构影响**：职责分离。`QueryTranslator` 输出**语言无关的概念结构**（如 `{terms: [...], filters: [...]}` 或按源的 `{source: [概念词]}`）；`QueryBuilder` 负责**把概念结构按目标库语法组装成最终串**。翻译与语法适配解耦，符合单一职责。
- **后续扩展 WoS/Scopus**：加库只需新增一个 `QueryBuilder` 分支（或子类），**不改 QueryTranslator**。翻译逻辑复用，语法逻辑按库隔离。
- **对现有测试影响**：`test_query_translator.py` 的断言需从"空格串"改为"概念结构"（或保留 `translate` 返回串、另加 `build` 返回最终串，二者共存）。`test_search_service.py` 单源断言需确认 CNKI 走 QueryBuilder 后仍透传原串（`Q`/`量子计算`）。

### 2.4 方案 C：每个 Adapter 内部生成 query

```
每个 Adapter.search 内部：把 keyword 翻译/组装成自己的语法
```

- **架构影响**：语法逻辑散落在各 Adapter，破坏 Adapter 的"只做检索+解析"稳定边界；翻译逻辑重复（每个 Adapter 都要查词典）。与 v0.8.0 审计（`query_translation_audit.md`）否决方案 C 的理由一致。
- **后续扩展 WoS/Scopus**：每个新库 Adapter 都要内嵌翻译+语法，重复且难维护。
- **对现有测试影响**：改动面最大——每个 Adapter 测试都要加翻译/语法断言；且违反"不修改 Adapter"约束。

### 2.5 方案对比

| 维度 | 方案 A（Translator 直出） | 方案 B（Translator+Builder） | 方案 C（Adapter 内嵌） |
| --- | --- | --- | --- |
| 职责分离 | 差（翻译+语法耦合） | **好**（翻译/语法解耦） | 差（语法散落+翻译重复） |
| 扩展 WoS/Scopus | 中（改 Translator） | **好**（只加 Builder 分支） | 差（改每个 Adapter） |
| 对现有测试影响 | 中（改 translator 断言） | 中（改 translator 断言 + 加 builder 测试） | 大（改每个 Adapter 测试） |
| 是否改 Adapter | 否 | 否 | **是**（违反约束） |
| 推荐度 | 不推荐 | **推荐** | 不推荐 |

**推荐方案 B**：`QueryTranslator` 输出概念结构，`QueryBuilder` 按库生成最终 query。翻译与语法适配解耦，扩展性最好，且不改 Adapter。

## 三、设计接口（只设计）

### 3.1 QueryBuilder 接口

```python
class QueryBuilder:
    """按目标数据库语法，把翻译后的概念组装为最终检索串。"""

    def build(self, source: str, translated_terms: list[str]) -> str:
        """为指定数据源生成检索串。

        translated_terms: QueryTranslator 输出的概念词列表（语言无关）。
        返回：该数据库可识别的最终 query 串。
        """
```

### 3.2 输出示例

**IEEE**（`translated_terms = ["terahertz", "THz", "integrated sensing and communication", "ISAC"]`）：

```
(terahertz OR THz)
AND
("integrated sensing and communication" OR ISAC)
```

**CNKI**（`translated_terms = ["太赫兹", "通感一体化"]`）：

```
太赫兹 通感一体化
```

### 3.3 内部策略（设计）

`QueryBuilder` 按 `source` 分派到不同策略：

```python
# 伪代码
class QueryBuilder:
    def build(self, source, translated_terms):
        if source == "IEEE Xplore":
            return self._build_ieee(translated_terms)   # 布尔 + 引号短语
        if source in ("CNKI", "万方"):
            return self._build_chinese(translated_terms)  # 透传/空格
        return " ".join(translated_terms)                # 未知源默认空格串
```

- `_build_ieee`：把概念词分组（同义词组 OR、组间 AND），多词概念加引号 `"..."`，单次概念不加；
- `_build_chinese`：中文库透传（或空格连接），保持与现有 `expanded.query_string` 兼容；
- 未知源：默认空格串（安全回退，不报语法错误）。

### 3.4 与 QueryTranslator 的协作（设计）

`QueryTranslator.translate` 从"直接输出串"演进为"输出概念结构"（或保留 `translate` 返回串 + 新增 `build` 返回最终串，二者共存以兼容现有测试）。`SearchService` 调用链变为：

```python
concepts = self._translator.translate(expanded, sources)   # {源: [概念词]}
for source in sources:
    query = self._builder.build(source, concepts[source])   # 该库最终串
    adapter.search(query, count)
```

## 四、评估风险

| 风险 | 等级 | 说明 |
| --- | --- | --- |
| **Boolean 语法错误** | 中 | 布尔串（`OR`/`AND`/引号/括号）需语法正确，否则 IEEE 引擎可能报错或返回空。引号必须成对、括号需平衡、未知词分组需兜底。需在 `_build_ieee` 内做语法校验（平衡括号/引号）与单测。 |
| **空结果风险** | 中 | 布尔串过度收窄（组间 AND 过多）可能空结果；引号短语若库内无完全匹配短语也可能空。需真实验证 + 保留"未命中词透传"兜底。 |
| **对已有 219 测试影响** | 中 | 方案 B 改动 `QueryTranslator` 输出（从空格串→概念结构）会波及 `test_query_translator.py` 断言；但 CNKI/万方透传路径若保持 `expanded.query_string` 不变，`test_search_service.py:56/61/71` 单源断言可保持。需同步 translator 断言 + 新增 builder 单测。 |
| **是否需要真实 IEEE 验证** | **是（必需）** | 布尔串对 IEEE 引擎的实际解析（引号短语、OR/AND 优先级、括号）必须真实验证，否则无法确认语法正确与空结果率。建议先跑 `v0.8_query_translation_validation_plan.md` 的 3 用例，再落地 `_build_ieee`。 |

## 五、结论

1. **Adapter 对 query 语法完全透明**（只填框不解析），布尔/引号/括号的支持取决于各库引擎；
2. **推荐方案 B**：`QueryTranslator` 输出概念结构，`QueryBuilder` 按库生成最终 query，翻译与语法适配解耦，扩展 WoS/Scopus 最友好，且不改 Adapter；
3. **接口**：`QueryBuilder.build(source, translated_terms) -> str`，IEEE 输出布尔+引号短语，CNKI/万方透传，未知源默认空格串；
4. **风险**：Boolean 语法错误（中）、空结果（中）、219 测试影响（中，需同步 translator 断言）、**真实 IEEE 验证必需**。
