日期：2026-09-03 性质：**只读分析，未修改任何源码，未新增功能**

## 0. 背景

v0.9.3 Phase 1 已完成 `LibraryRecord` 模型和 `LibraryStore` JSON 存储层。
本轮审计聚焦 GUI 层如何接入收藏能力，确保最小改动、零测试破坏。

## 1. 当前 GUI 结果展示结构

### 1.1 QTableWidget 列结构

```
RESULT_COLUMNS = ["标题", "作者", "来源", "年份", "类型", "数据库"]
# 6 列，索引 0-5
```

- 列 0（标题）：`QHeaderView.Stretch`（占满剩余空间）
- 列 1-5：`ResizeToContents`
- 行高：34px
- 选择模式：单行选择（`SingleSelection`）
- 编辑模式：`NoEditTriggers`（只读）
- 交替行色：`True`

### 1.2 self._results 数据格式

```python
self._results: list[dict] = []
# 每个元素是 SearchResult.to_dict() 的输出，包含：
# rank, title, authors, source, year, detail_url, document_type,
# database, abstract, doi, keywords, venue, authors_raw
```

数据流：`SearchService.search()` → `Worker.search_done.emit([r.to_dict()...])`
→ `MainWindow._on_search_done(results)` → `self._results = results`。

### 1.3 表格刷新位置

唯一刷新入口：`_populate_table(results: list[dict])`，在以下 3 处调用：
1. `_on_search_done(results)` — 检索完成
2. `_on_load_demo()` — 演示数据加载
3. 无其他调用点

### 1.4 演示数据加载流程

```python
def _on_load_demo(self) -> None:
    demo = load_demo_results()           # runtime/demo_results.json 或内置
    raw = demo["results"]                # list[dict]，6 条
    merged = ResultMerger.merge(...)     # 去重 → 5 条
    ranked = RankingService.rank(...)    # 排序
    self._results = [r.to_dict() for r in ranked]
    self._populate_table(self._results)  # 填充表格
    self.btn_detail.setEnabled(True)     # 启用操作按钮
```

### 1.5 分析回答

**收藏状态应该存在哪里？**
- 不应存在 `self._results`（那是检索结果，与用户行为无关）；
- 应存在 `LibraryStore` 中，通过 `id`（`uuid4.hex`）匹配；
- GUI 层需要维护一个 `self._library_ids: set[str]`（当前结果表中已收藏的 id 集合），
  每次 `_populate_table` 后从 `LibraryStore.load_all()` 加载并过滤出匹配项。

**是否应该修改表格列？**
- **不建议新增列**：
  1. 现有 6 列已较密集，新增列会压缩已有列宽度；
  2. `test_gui.py` 中 `test_search_done_populates_table` 通过 `self.table.item(0, 0)` 验证标题列，
     新增列会改变列索引，可能破坏既有测试；
  3. 收藏是低频操作，不需要在表格中频繁显示。
- 替代方案：底部按钮 + 状态栏反馈（见方案 A）。

**如何保持现有测试契约？**
- 不修改 `RESULT_COLUMNS`；
- 不修改 `_populate_table` 的列写入逻辑；
- 不修改 `self._results` 的数据结构（仍是 `list[dict]`）；
- 新增 `self._library_ids` 作为内部状态，不影响公开表面。

## 2. 收藏操作接入点方案比较

### 方案 A：底部按钮"收藏当前论文" ★推荐

**设计**：在 bottom bar 新增一个按钮，与 `btn_detail` / `btn_ieee_original` 并列。

```
[收藏当前选中] [打开全文页面] [访问IEEE原始站] [导出结果] ...
```

- 逻辑：选中行 → 从 `self._results[sel]` 提取元数据 → `LibraryRecord.from_search_result()`
  → `LibraryStore.save()` → 状态栏反馈"已收藏：{title}"；
- 启用态：与 `btn_detail` 同步（有选中行且有 title）；
- 反馈：状态栏文本，可选短暂 `QMessageBox.information`（可关闭）。

| 维度 | 评估 |
| --- | --- |
| 实现复杂度 | **低** — 新增 1 个按钮 + 1 个 handler，~20 行代码 |
| 用户体验 | **中** — 直观，但每次收藏需先选中行再点按钮 |
| 对现有测试影响 | **零** — 不修改 RESULT_COLUMNS、不修改表格结构 |
| 后续扩展 | **好** — 可扩展为"编辑收藏"按钮、批量收藏等 |

### 方案 B：结果表增加"收藏"列（星标）

**设计**：在表格最右侧新增第 7 列"收藏"，每行显示一个可点击的星标图标。

- 需要修改 `RESULT_COLUMNS`、`_populate_table`、`_build_results_card`；
- 每行需要存储 `LibraryRecord.id` 作为 `Qt.UserRole` 附加数据；
- 点击星标 → 切换收藏状态。

| 维度 | 评估 |
| --- | --- |
| 实现复杂度 | **高** — 修改列结构、单元格点击事件、图标绘制 |
| 用户体验 | **高** — 可视化直观，可批量浏览收藏状态 |
| 对现有测试影响 | **中** — `test_search_done_populates_table` 验证 `item(0,0)` 标题列不受影响，
  但列数变化可能影响其他测试（如 `test_export_button_connected` 中导出字段顺序） |
| 后续扩展 | **好** — 可加标签列、阅读状态列等 |

### 方案 C：右键菜单收藏

**设计**：在 QTableWidget 上启用右键菜单，包含"收藏"选项。

- 需要重写 `contextMenuEvent`；
- 菜单项：收藏、查看收藏详情（后续）、编辑标签（后续）。

| 维度 | 评估 |
| --- | --- |
| 实现复杂度 | **中** — 需实现 `contextMenuEvent` + 菜单构建 |
| 用户体验 | **中** — 需要用户知道右键可用 |
| 对现有测试影响 | **零** — 不修改表格结构 |
| 后续扩展 | **好** — 右键菜单天然适合扩展（收藏、标签、备注、删除等） |

### 推荐：方案 A + C 组合

v0.9.3 Phase 1.5 最小实现：
1. **方案 A**（底部按钮）——核心收藏入口，实现简单、测试零影响；
2. **方案 C**（右键菜单）——作为后续增强，不阻塞 Phase 1.5。

方案 B（新增列）留待 v0.9.4 评估，因其修改列结构的风险高于收益。

## 3. LibraryStore 接入设计

### 3.1 是否需要单例？

**推荐：是。**

- `LibraryStore` 无状态（文件路径固定），单例可避免重复文件 I/O；
- 调用路径：`MainWindow.__init__` → `self._library_store = LibraryStore()`，
  后续所有操作复用同一实例；
- 不需要全局单例（`_library_store` 作为 `MainWindow` 实例属性即可）。

### 3.2 是否需要缓存？

**推荐：是，轻量缓存。**

- 收藏数据量通常 < 5000 条，每次操作都读 JSON 文件效率不高；
- 缓存策略：`self._library_cache: list[LibraryRecord]`，
  在 `_populate_table` 后加载一次，收藏/删除后更新缓存；
- 缓存失效：`save()` / `remove()` 后更新内存缓存 + 写文件。

### 3.3 是否需要启动时加载收藏状态？

**推荐：是，但延迟到首次 `_populate_table`。**

- 启动时不加载（避免启动延迟）；
- 首次 `_populate_table` 时加载 `LibraryStore.load_all()`，
  过滤出当前 `self._results` 中已收藏的 id，存入 `self._library_ids`；
- 后续 `_populate_table` 时增量更新（新结果 → 检查是否已收藏）。

### 3.4 GUI 调用路径

```
用户点击"收藏当前选中"
  ↓
MainWindow._on_favorite()
  ↓
sel = self.table.currentRow()
  ↓
data = self._results[sel]          # dict from SearchResult.to_dict()
  ↓
record = LibraryRecord.from_search_result(data)
  ↓
self._library_store.save(record)
  ↓
self._library_cache.append(record)  # 更新缓存
self._library_ids.add(record.id)    # 更新已收藏集合
  ↓
self._set_status(f"已收藏：{record.title}")
```

## 4. 收藏状态同步分析

### 4.1 已收藏论文如何显示？

**Phase 1.5 最小方案：不显示在表格中，仅通过状态栏反馈。**

- 用户点击收藏 → 状态栏显示"已收藏：{title}"；
- 不修改表格列、不添加星标图标；
- 如需可视化，留待 Phase 1.6（方案 B 或 C）。

### 4.2 如何判断当前结果是否已收藏？

**通过 `LibraryRecord.id` 匹配。**

- `LibraryRecord.id` 是 `uuid4().hex`（32 字符），每次 `from_search_result` 生成新 id；
- 问题：同一篇论文被检索两次会产生两个不同的 id！
- 解决方案：
  1. **Phase 1.5 最小方案**：不处理重复 id 问题，每次收藏生成新 id，
     用户可收藏同一论文多次（可接受，数据量小）；
  2. **Phase 1.6 增强**：使用 `title + authors + year` 哈希作为稳定 id，
     确保同一论文多次检索产生相同 id；
  3. **Phase 1.7 优化**：引入 `doi` 作为主键（如果可用），`title_hash` 作为备用。

### 4.3 是否需要 title 匹配？

**Phase 1.5 不需要。**

- 当前 `LibraryRecord.id` 是随机 uuid，无法通过 title 反向匹配；
- 如需"判断是否已收藏"功能，需先重构 id 生成策略（见上）；
- Phase 1.5 聚焦"收藏写入"功能，"已收藏状态显示"留待后续。

### 4.4 是否需要生成稳定 id？

**Phase 1.5 不需要，Phase 1.6 建议引入。**

- 当前 `uuid4().hex` 适合写入，但不适合跨检索匹配；
- 建议 Phase 1.6 引入 `LibraryRecord.generate_stable_id(title, authors, year, doi)` 函数，
  优先使用 `doi`（如果非空），否则使用 `hashlib.sha256(f"{title}{''.join(authors)}{year}".encode()).hexdigest()[:16]`。
