## 一、审计结论

当前工作树**不具备直接发布条件**。功能实现和真实 IEEE 全链路验收已经完成，但发布元数据、功能文档、测试数字口径和 Git 提交边界尚未整理完成。

主要阻塞项：

1. 统一版本仍为 `v0.7.1`，需要升级为 `v0.8.2`。
2. README、架构文档、`version.py` 的功能描述没有同步 v0.8.x 跨语言检索能力。
3. 版本号硬编码在测试和验收脚本中，升级版本后会有已知断言失败。
4. README 的测试数字仍为 `210 passed`，当前裸 `pytest` 实测为 `259 passed`。
5. v0.8.x 代码、测试和文档全部尚未提交。
6. `v0.8_ieee_metadata_parser_implementation.md` 将 `pytest tests/` 的 223 与裸 `pytest` 的 255 混为不同基线，导致“255 与实际不一致”的结论错误，需要更正。

建议：**先完成发布整理，再创建 v0.8.2 release commit；本轮不建议直接打 tag 或发布压缩包。**

### 4.3 255 与 223 的口径解释

早期文档的测试数字链条是：

```text
210 → 219 → 230 → 243 → 255
```

这条链条使用的是裸 `pytest` 口径，包含根目录 36 个 PoC 测试。

IEEE Parser 实现阶段记录的：

```text
219（基线）→ 223（新增 4 个 parser 测试）
```

使用的是 `pytest tests/` 口径，不包含根目录 36 个 PoC 测试。

因此：

```text
255 = 219 + 36
259 = 223 + 36
```

不是测试丢失，而是测试范围不同。发布前必须修正 `v0.8_ieee_metadata_parser_implementation.md` 中“255 与仓库实际数量不一致”的表述，统一在报告中明确采用裸 `pytest` 还是 `pytest tests/`。

### 4.4 测试发布建议

发布说明建议统一采用：

```text
python -m pytest -q：259 passed, 0 failed, 0 skipped
```

同时可在测试说明中补充：

```text
pytest tests/ -q：223 passed
```

两者不能在同一处不加范围地并列，否则会继续造成数字不一致误解。
